# Size Classes

Mnemosyne routes a request through a fixed small-allocation table or through
the large/huge mapper. The boundary is a compile-time constant, so the hot
route does not need a policy object, heap allocation, or a per-request search.

## The two regimes

For a non-zero request `r`, the small route is selected when
`r <= MAX_SMALL_ALLOC_SIZE`. The current constants are:

| Regime | Request range | Route |
|---|---:|---|
| Small | 1 B–16 KiB | One of 52 page-local size classes |
| Large / huge | Greater than 16 KiB | `allocate_large_or_huge` and its backend mapping policy |

`size_to_class(r)` returns `None` above the small ceiling. The allocation
entry points reject zero-sized requests before routing; the lower-level mapper
keeps `size_to_class(0) == Some(0)` as the historical already-adjusted minimum
case.

The table is authoritative in `mnemosyne-core::size_class`:

```text
class_to_size(0)  = 16 B
class_to_size(7)  = 128 B
class_to_size(19) = 512 B
class_to_size(31) = 2 KiB
class_to_size(43) = 8 KiB
class_to_size(44) = 9 KiB
class_to_size(51) = 16 KiB
```

The complete class sequence is one 16-byte step through 128 B, one 32-byte
step through 512 B, one 128-byte step through 2 KiB, one 512-byte step through
8 KiB, and one 1024-byte step through 16 KiB. Thus the 8–16 KiB band has eight
classes rather than four. A request of 8193 B maps to the 9216 B class, while
16384 B is still small and 16385 B takes the large/huge route.

## Mapping and fragmentation

The mapper rounds the request to a 16-byte granule before loading the
compile-time `SIZE_TO_CLASS` table. The table has
`MAX_SMALL_ALLOC_SIZE / MIN_BLOCK_SIZE + 1` entries: 1025 one-byte entries for
the current 16 KiB ceiling. Its entries are generated by the arithmetic
piecewise mapper at compile time, so runtime classification is a bounded table
lookup rather than a division/search sequence.

Let `b(r) = class_to_size(size_to_class(r))`. The rounded block is never
smaller than the request, and the internal slack is

```text
slack(r) = b(r) - r >= 0
```

Away from a class boundary, the slack is less than the gap to the next class.
In the 8–16 KiB band that gap is 1024 B, so `slack(r) < 1024 B`. Immediately
above 8192 B, the largest relative slack is therefore about 12.5%; the 1024-B
spacing is the reason the current table reduces the previous 2048-B-band
bound of about 25%.

This is a space-versus-metadata decision. More classes reduce rounding waste
but add per-class page metadata and can reduce reuse when a workload touches
many rarely used classes. Mnemosyne keeps the class list in a fixed array and
stores per-class occupancy in the allocator statistics, so the tradeoff is
visible rather than hidden in an unbounded map.

## Page density

Each small page serves exactly one class. For class block size `b`, the maximum
number of blocks on a page is derived as

```text
blocks_per_page(b) = floor(PAGE_SIZE / b)
```

With `PAGE_SIZE = 64 KiB`, representative densities are:

| Class | Block size | Maximum blocks/page |
|---:|---:|---:|
| 0 | 16 B | 4096 |
| 7 | 128 B | 512 |
| 19 | 512 B | 128 |
| 31 | 2048 B | 32 |
| 43 | 8192 B | 8 |
| 44 | 9216 B | 7 |
| 51 | 16384 B | 4 |

`class_to_max_blocks` computes the same quotient from the canonical class
table. The segment geometry is `2 MiB / 64 KiB = 32` pages. Page-local
classification keeps each page homogeneous, which lets the free-list and
block arithmetic use one class size without per-block size metadata.

The page-local design follows the allocator locality principle described by
Microsoft Research for mimalloc: sharding free lists by page reduces ownership
contention and keeps allocation state near the objects it serves. The cited
paper's measurements are evidence for that external design, not a performance
claim about Mnemosyne; Mnemosyne performance claims require its own controlled
benchmarks.

See [Mimalloc: Free List Sharding in Action, sections 2.1 and 3.1](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/06/mimalloc-tr-v1.pdf)
for the page-local free-list and page-geometry rationale.

## What this chapter does not cover

`KernelResourceBudget` and `OccupancyLimits` are compile-time occupancy
limiters for GPU launch shapes. They are not part of the CPU size-class path.
The allocator's per-class statistics and retained-segment behavior are covered
in the profiling and decay chapters.
